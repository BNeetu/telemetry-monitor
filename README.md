# Angular + Electron Telemetry Monitor

Windows desktop monitoring application built with **Angular 19**, **Electron**, and **TypeScript**. It displays real-time telemetry for Velocity, Pressure, and Temperature from a simulated backend controller.

## Features

- Real-time dashboard with circular gauges, live values, status indicators, and trend graphs
- Backend simulation via `GET /api/dashboard` (1-second updates, ±10% variation, drift correction every 5 cycles)
- Client-side unit conversion (no extra API calls)
- Light/Dark theme switching without reload
- CSV and Excel export
- Chart zoom, pan, and tooltips
- Connection, loading, and error states

## Prerequisites

- Node.js 18+ (tested with Node 24)
- npm 9+

## Setup Instructions

### 1. Install dependencies

From the project root:

```bash
npm install
npm run install:all
```

Or install each part separately:

```bash
npm install --prefix backend
npm install --prefix frontend
```

### 2. Run the full application

From the project root, run:

```bash
npm start
```

This starts the backend API, Angular dev server, and Electron desktop window together. Use `npm run dev` for the same workflow.

Services:
- Backend API: `http://localhost:3000/api/dashboard`
- Angular UI: `http://localhost:4200`

### 3. Run web-only (without Electron)

Terminal 1:

```bash
npm run backend
```

Terminal 2:

```bash
npm run frontend
```

Open `http://localhost:4200` in a browser.

### 4. Production desktop build

```bash
npm run start:prod
```

This builds the backend and frontend, starts the compiled API, waits for its health check, and opens the built Angular app in Electron.

## Deploy the Web App

### Backend on Render

Create a Render Blueprint from this repository and select `render.yaml`. It deploys the API from `backend/`; after it is live, copy the service URL (for example, `https://telemetry-monitor-api.onrender.com`). The health check is available at `/api/health`.

### Frontend on Vercel

- Set the Vercel project's **Root Directory** to `frontend`.
- Set its **Build Command** to `npm run build` and **Output Directory** to `dist/frontend/browser`.
- The Vercel build defaults to `https://telemetry-monitor-api.onrender.com`, matching the Render service name in `render.yaml`. Deploy the backend first. If Render gives the service a different URL, set `TELEMETRY_API_URL` in Vercel's Production (and Preview, if used) environment to the service's HTTPS base URL, without `/api/dashboard`.
- Redeploy after changing the variable. The production Angular build embeds the selected URL; it does not read Vercel variables at runtime.

Local development continues to use `http://localhost:3000`.

## Architecture & Technical Decisions

### Backend (Express + TypeScript)

- A singleton `TelemetrySimulator` generates values every second.
- Each sensor keeps the latest **100** history points in memory.
- Values vary randomly each tick and drift back toward baseline every **5th** update (see tuning note below).
- Seed history on startup is generated by running the same update rule forward from baseline, so the very first render already looks like a live signal instead of a flat line, and the seed's final value matches the sensor's live current value exactly (no discontinuity when real ticks begin).
- A defensive clamp (±22% of baseline) prevents runaway drift over long sessions; in normal operation the tuned noise/reversion balance keeps values well inside this band, so it rarely engages.
- `GET /api/dashboard` returns the current snapshot in the required JSON format.

### Frontend (Angular)

- **TelemetryService** polls the API every second using RxJS `interval`.
- **UnitConversionService** converts values client-side for gauges, labels, and charts.
- **ThemeService** uses CSS variables and `data-theme` for instant theme switching.
- **ExportService** exports current telemetry snapshots to CSV/XLSX using `file-saver` and `xlsx`.
- Components are standalone for simpler structure and lazy-friendly architecture.

### Electron

- Loads the Angular dev server in development.
- Loads the built Angular app from `frontend/dist` in production.
- Context isolation enabled; Node integration disabled in the renderer.

### UI / Charts

- Custom SVG circular gauges for smooth value animation.
- Chart.js with zoom/pan plugin for live trend graphs (mouse wheel/pinch to zoom, drag to pan, small reset-zoom button per chart).
- Responsive card layout with status coloring (Normal / Warning / Critical).

## Assumptions

1. Backend base units are **cm/s**, **mbar**, and **°C** (matching the sample response).
2. Status thresholds are configured in the frontend based on converted values:
   - Velocity: Normal 20–75 cm/s, Warning outside that range, Critical below 10 or above 90 cm/s
   - Pressure: Normal 970–1050 mbar, with warning/critical bands beyond that
   - Temperature: Normal 15–32 °C, with warning/critical bands beyond that
3. Export reflects the currently selected units per parameter (not the raw backend units) and covers the last 100 samples currently held in memory, since the backend itself only retains a rolling 100-sample window per parameter.
4. Electron is used as the desktop shell; the same UI works in a browser for development.
5. CORS is enabled on the backend for local development.
6. **Simulation tuning**: the spec's "randomly vary by ~10%, then gradually return every 5 cycles" is implemented literally, but with a per-tick noise magnitude (~2.5%) tuned so that a run of several ticks compounds to roughly the ~10% excursion described, rather than drawing a full ±10% step every single second. A pure ±10%-per-tick random walk with only a weak periodic correction turned out to be statistically unstable over longer sessions — in testing it could wander to less than half or nearly double the baseline value (e.g. pressure readings well outside any physically plausible range). The tuned version keeps the same architecture (random walk + periodic partial reversion) but calibrates the magnitudes so the dashboard spends most of its time in `Normal`, transitions into `Warning` periodically, and only occasionally reaches `Critical` — matching both the gentle drift shown in the assessment's own sample response (velocity moving from 180.2 to 185.4 over 5 samples) and a realistic, demo-friendly range for all three parameters. A hard ±22% safety clamp is also in place as a last-resort bound.
